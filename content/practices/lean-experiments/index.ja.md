## この方法の使い方

{{% section %}}

### サンプルアジェンダとプロンプト

1. **チームにLean Experimentationを紹介します**

   Lean Experimentsとは何か、なぜ行うのか、一般的な実験のタイプを紹介します。

   > _「Lean Experimentsは、極度の不確実性の条件下で新しい製品とサービスを作成するためのLean Startupアプローチに基づいています。Lean Experimentsは、製品に関するリスクの高い仮定を検証または無効化するための証拠を迅速かつ安価に収集するように設計されています。」_

   ![Risks Without Validation](images/lean-experiment-1.png)

   一般的な実験のタイプ：

   **_A/B Test_**

   製品または機能の2つのバージョンを比較して、どちらが最もパフォーマンスが高いかを確認します。体験とビジネスモデルの小さな増分最適化のための大規模なユーザーセットで最もよく機能します。

   **_Concierge Test_**

   複雑な自動化された技術ソリューションを、顧客と直接対話する人間に置き換える技術。誰かが私たちの製品を望んでいるかどうかを検証するのに役立ちます。

   **_Wizard of Oz Test_**

   製品バックエンドを人間に置き換える技術。顧客は、自動化されたソリューションと対話していると信じています。誰かが私たちの製品を望んでいるかどうかを検証するのに役立ちます。

   **_Smoke Test_**

   一般的に、製品の価値提案を説明し、製品が利用可能になる前に顧客に製品にサインアップするよう依頼するWebサイト。誰かが私たちの製品を望んでいるかどうかを検証するのに役立ちます。

   {{< callout >}}
   **ヒント**: 独自の紹介デッキと例を考え出すことを自由に行ってください。部屋にいくつかの追加例を促して、正しい方向に考えさせます。自分の製品スペースに匹敵する例を見つけることができれば、ボーナスポイントです。
   {{< /callout >}}

1. **チームの「信念の飛躍」仮定をカタログ化します**

   この用語をホワイトボードに追加します。定義を含めて、チームが演習全体でそれを参照できるようにします(間違っている場合、製品は失敗する可能性が高い仮定)。

   チームに2分間、付箋に信念の飛躍仮定をブレインストーミングするように依頼します。チームメンバーが2つ以上思いついた場合は、最も重要なものに自己編集するように依頼します。

   製品の未検証の信念の飛躍仮定をホワイトボードにカタログ化します。

   {{< callout >}}
   **ヒント**: 否定的ではなく肯定的に仮定をフレーミングしてみてください(ユーザーは見知らぬ人の車に乗ることに安全を感じるでしょう対誰も見知らぬ人の車に乗りたくないでしょう)。これにより、私たちが持っている/必要とする証拠の量を反映しやすくなります。
   {{< /callout >}}

   いくつか以上の信念の飛躍仮定が発生した場合は、最初に焦点を当てる1つに優先順位を付けます。[Assumptions](/practices/assumptions/)プラクティスを使用するか、Y軸に「プロジェクトを停止する可能性が高い」対「プロジェクトを停止する可能性が低い」、X軸に「より多くの証拠が必要」対「多くの証拠がある」の2x2を検討してください。より多くの証拠が必要なプロジェクトを停止する可能性が高い仮定がターゲットです。

1. **仮定を偽造可能な仮説に変換する必要があることを説明します：**

   > **_[特定のテスト可能なアクション]_**が**_[期待される測定可能な結果]_**を促進します

   仮説、実験、測定を追跡するために使用する形式/テンプレートを紹介します。

   例えば：

   - [Lean Experiment Template (PDF)](/files/Lean_Hypothesis_Template_Public.pdf)
   - [Strategyzer Test Card (PDF)](https://assets.strategyzer.com/assets/resources/the-test-card.pdf)

   以下のそれぞれが何を表すかを説明します：

   - Hypothesis — 私たちが真実であると信じていること
   - Experiment — 仮説を検証するために実行するテスト
   - Measurement — 検証のために探す信号
   - Outcome — 成功および失敗基準

   {{< callout >}}
   **ヒント**: 実験を時間制限することを忘れないでください。実験を実行する時間の長さは、事前に定義する必要があります。
   {{< /callout >}}

   {{< callout >}}
   **ヒント**: チームが良いメトリックが何であるかに精通していない場合は、入門書または例を提供することを検討してください
   {{< /callout >}}

1. **実験を生成します**

   各チームメンバーに紙を配布し、次のように指示します：

   - Hypothesis & Experimentテンプレートの形式をコピーする
   - 信念の飛躍仮定を偽造可能な仮説として書く

   {{< callout >}}
   **ヒント**: 4人以上の参加者がいる場合は、実験を生成するためにチームに分割することを検討してください
   {{< /callout >}}

   {{< callout >}}
   **ヒント**: テンプレートを印刷したり、電子メール/共有したり、ワークショップの前にデジタルワークスペースを作成して共有したりします。
   {{< /callout >}}

   このMiroボードを自由にコピーしてください：[Validation Research/MVP Experiment on Miro](https://miro.com/app/board/o9J_lGThxtc=/)  
   全員に5分間個別に、仮説をテストするための実験と関連する測定可能な結果を考えるように促します。

1. **実験を共有します**

   時間が終了したら、各チームメンバーに(1人ずつ)シートを壁に貼り付けてもらい、グループディスカッションのために実験の詳細を共有してもらいます。

   {{< callout >}}
   **ヒント**: チームのフィードバックからの実験の反復を奨励する必要があります。
   {{< /callout >}}

   全員に5分間実験を共有してもらいます。

1. **実験を選択します**

   最良の実験は、最大の学習のために最小限の努力を必要とすることを説明します。チームメンバーに、実行するのが最良だと思う実験に静かにドット投票(グループサイズと実験の数に応じて1または2票)してもらいます。

   {{< callout >}}
   **ヒント**: 実験を洗練できると思う場合は、チームに実験を再設計するように促すことを検討してください。異なるチームメンバーに、$200で2日、$2000で2週間、$20,000で2か月かかる同じ仮説の実験を作成するように割り当てます。これにより、実験の適切なサイズを見つけ、より小さく学ぶ方法を奨励するのに役立ちます。
   {{< /callout >}}

1. **実験を評価する方法について議論します**

   実験が選択されたら、それを評価する方法について話し合います。通常、実験は3つの学習結果のいずれかをもたらし、それぞれに期待される次のステップがあります：

   - Uncertainty > もっとテストして、実験を反復する可能性があります
   - Validated > 進捗
   - Invalidated > ピボット

   いずれの結果についても、実験の結果と計画された次のステップを記録します。活用する良いリソースは、Strategyz​​erの[The Learning Card](https://assets.strategyzer.com/assets/resources/the-learning-card.pdf)です。

   {{< callout >}}
   **ヒント**: 実験にスーパー失敗条件を設定することは良い習慣です。これは、実験自体に問題がある可能性があることを示すほどひどい失敗です。それをテストするために何かが真実であると信じるべきなので、壮大な失敗はありそうにないはずです。
   {{< /callout >}}

1. **次のステップとアクションアイテムを計画します**

   実験を実行するためにチームメンバーが取るべきアクションをブレインストーミングして割り当てます。

1. **実験トラッカーを作成します**

   このセッションで選択されなかった実験をバックログで追跡します。これらの実験を定期的にレビューし、製品の方向性を検証するために関連する実験を実装します。特に製品の方向性が変更された場合。
   {{% /section %}}

### 成功/期待される成果

### ファシリテーターのメモとヒント

検証する仮定が多数ある場合は、上記の最後のステップで提案されているように、仮説/実験トラッカーでフォローアップすることを検討してください。これにより、チームはどの仮説をどの順序でテストすべきか、およびそれらに関連する実験を視覚化するのに役立ちます。
