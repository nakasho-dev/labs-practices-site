## この方法の使い方

{{% section %}}

### サンプルアジェンダとプロンプト

1. ミーティングの会話をフレーミングすることから始めます。最近受け入れられた、または進行中のストーリーまたは受け入れ環境での最新の機能の現状を簡単に要約することで、この次のイテレーションに入る際に現在どこにいるかについて全員が整列するように、必要に応じて全体的なプロジェクトコンテキストを設定するのに役立ちます。新しいユーザーストーリーのアークをレビューして、それらが製品に追加するものを概説します。利用可能な場合は、ユーザーインターフェースのモックアップを提示します。

1. 最初のユーザーストーリーを読んで、ビジネス価値、ユーザー価値、および受け入れ基準を説明します。参加者が質問できるようにし、必要に応じて明確化を提供します。

   {{< callout >}}
   **ヒント**: チームのすべてのメンバーが、自分が快適に感じる見積もりを提供するために必要な明確化を得るためのスペースを許可します。個人の性格が会話を支配したり、チーム全体の理解を妨げるアプローチを指示したりしないように注意してください。
   {{< /callout >}}

1. エンジニアに、ユーザーストーリーを見積もる準備ができているかどうかを示すように促し、そうであれば、ストーリーポイント見積もりに同時に投票することで、ストーリーの相対的な複雑さを見積もるように促します。

   見積もりのヒントについては、以下の[見積もりの簡単なガイド](#estimation)を参照してください。

1. 見積もりに合意がある場合は、ユーザーストーリーに見積もり結果のラベルを付けてバックログに昇格させ、このストーリーの優先順位をチームに示します。それ以外の場合、合意がない場合は、エンジニアに議論を促し、チームが満足する合意が得られるまで必要に応じて再見積もりします。

   {{< callout >}}
   **ヒント1**: 会話が長くかかりすぎたり、このユーザーストーリーの範囲から大きく逸脱したりしないようにしてください。このストーリーの範囲について大量の不確実性または意見の相違がある場合、このストーリーを将来のIPMで合理的に見積もることができる前に、調査または実験のためのchoreをプロダクトバックログに追加する必要があるかもしれません。
   {{< /callout >}}

   {{< callout >}}
   **ヒント2**: ユーザーストーリーは実装に依存しないままにする必要があります。相対的な複雑さを見積もる際に実装に関する議論が自然に発生しますが、これらの議論を高レベルに保ち、実装の深い掘り下げは保留にしてください。
   {{< /callout >}}

1. このミーティングのために準備された残りのユーザーストーリーについて、ステップ2〜4を繰り返します。

   {{< callout >}}
   **ヒント**: 利用可能な時間を使用して、準備されたユーザーストーリーをできるだけ多く議論して見積もります。必要に応じて、一部のユーザーストーリーは次のIteration Planning Meetingに延期される場合があります。計画より多くの時間を取ることは避け、チームから貴重なエネルギーを奪わないでください
   {{< /callout >}}

1. ミーティングの最後の10分間で、エンジニアリングchoreを含むプロダクトバックログアイテムの相対的な優先順位をレビューして議論します。

   {{< callout >}}
   **ヒント**: エンジニアに、プロダクトバックログに昇格させたいchoreの範囲と重要性についてアドバイスするように促します。
   {{< /callout >}}

### 成功/期待される成果

まず、チームは議論されたプロダクトバックログアイテムの範囲と相対的な複雑さについて共有理解を持つべきです。次に、アイテムはプロダクトバックログに追加され、現在の優先順位に従ってソートされたままです。チームは、次のイテレーションで来る作業について整列し、エネルギーを感じてIPMから離れるべきです。
{{% /section %}}

{{% section %}}

### ファシリテーターのメモとヒント

- IPMをより効率的に実行するために、ミーティングで議論されるユーザーストーリーが事前に適切にグルーミングされていることを確認してください。デザイナーとエンジニアと協力して、ストーリーが実行可能でINVEST基準を満たしていることを確認してください。ミーティング中に慌ててストーリーを書くことは避けてください。
- エンジニアに必要なchoreを作成するように促し、必要に応じてエンジニアと協力して、IPMの前にそれらのchoreに優先順位を付けてグルーミングしてください。
- 議論して見積もるためのユーザーストーリーがすでに準備されていて、プロダクトバックログに平均チームベロシティに従って3イテレーション未満の作業が含まれている場合にのみIPMを開催してください。遠すぎる見積もりをすると、見積もりが正確でなくなり、チームがそれらのユーザーストーリーの作業を開始するまでにコンテキストを忘れる可能性があります。
  {{% /section %}}

{{% section %}}

### 見積もりの簡単なガイド {id=estimation}

- プロダクトバックログに3イテレーション以上前に見積もられたユーザーストーリーがある場合、チームが役立つと同意すれば、IPMにスケジュールされた時間を使用して、今後のユーザーストーリーをレビューして再見積もりすることを検討してください。
- 複雑さは、プロダクトバックログ内の他のユーザーストーリーまたはベースラインユーザーストーリーに対して相対的に見積もることができます。
- 相対的な複雑さは、作業を完了するのにかかる時間よりも、ユーザーストーリーのサイズを見積もるための簡単でより信頼性の高い方法です。
- 見積もりは通常「ストーリーポイント」を使用して定量化され、チームは一貫性のために、プロジェクト全体で使用するポイントスケール（例：Fibonacci、線形、指数）に事前に整列する必要があります。
- バイアスを避けるために、見積もりは同時に行うことが重要です。これを行う良い方法は、参加者に3のカウントで投票してもらうことです。
- 大きなストーリーポイント見積もりは、結果として得られるより小さなストーリーがユーザーにとって価値がある場合、ユーザーストーリーを分割する必要があることを示唆する場合があります。
- 受け入れテスト/検証以外にほとんどまたはまったく作業がない場合、ユーザーストーリーは0ストーリーポイントを持つと見積もられる場合があります。
- ストーリーポイント見積もりが不正確であっても問題ありません。同じ製品で作業している同じチームは、不一致が平均化されるにつれて、時間の経過とともにより正確で一貫した見積もりを行います。
- 見積もりは通常、エンジニア、または作業を提供する人によってのみ行われる必要があります。TesterやArchitectなどの他の役割は、相対的な複雑さの十分な理解がある場合に貢献できます。

## 関連プラクティス

### Sprint Planning vs. Iteration Planning

[Scrum「Sprints」](<https://en.wikipedia.org/wiki/Scrum_(software_development)#Sprint_planning>)と「Iterations」はどちらもタイムボックス化された活動ですが、計画の実施方法に影響を与えるいくつかの違いがあります：

{{< table "table" >}}
| | Sprint Planning | Iteration Planning |
| ---- | ---- | ---- |
| **前提条件** | • Sprint Goal<br>• 優先順位付けされたProduct Backlog | • 優先順位付けされたProduct Backlog<br>• レビューされるユーザーストーリー |
| **目的** | • Sprintの目標について整列<br>• Sprintの範囲を交渉して計画（a.k.a. Sprint Backlog） | • 現在の範囲と優先順位（すなわちProduct Backlog）の共有理解を維持 |
| **活動** | • ユーザーストーリーのレビュー<br>• Product BacklogからSprint Backlogへのユーザーストーリーのプル | • ユーザーストーリーのレビュー<br> • ユーザーストーリーの見積もり<br> • 優先順位に従ってProduct Backlogへのユーザーストーリーの昇格 |
| **出力** | • チームがSprintの終わりに提供してデモすることをコミットする、優先順位付けされていないSprint Backlog | • 優先順位付けされたProduct Backlog<br> • Iteration中に提供およびデモされる可能性のある作業の見積もり |
| **参加者** | • Product Owner<br> • Engineers | • コアチーム |
{{</ table >}}
