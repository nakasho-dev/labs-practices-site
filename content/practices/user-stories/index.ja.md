## この方法の使い方

3つの主要なプロジェクトフェーズに対してストーリーを準備する必要があります：

- 次の[Iteration Planning Meeting](/practices/ipm/)に向けてグルーミングされ準備ができているユーザーストーリー（1〜2週間先）
- 高忠実度デザインの準備ができているが、すべての詳細が確定していないユーザーストーリー（2〜4週間先）
- 製品がどこに向かっているかを示し、調査活動に情報を提供するための大まかなアイデアでスケッチされたユーザーストーリー（1〜3ヶ月先）

### サンプルアジェンダとプロンプト

1. ユーザーストーリーに分解するアイデア、フィーチャー、またはユーザーフローをレビューすることから始めます。フィーチャーまたはユーザーフローを生成するために、Story Mapping演習またはチームとのカジュアルなアイデアセッションを行っている可能性があります。

2. **タイトルを書きます。** 短く説明的にします。実行可能なタイトルは、バックログがチーム全体にとって理解しやすいことを保証します。

   {{< callout >}}
   タイトルの例：_営業担当者はPDFとして販売提案をダウンロードできる_

   {{< /callout >}}

3. **説明を書きます。** 「[ペルソナ]として … 私は … したい … そうすることで …」形式を使用して、このストーリーがユーザーの視点から提供する価値を説明します。

   {{% callout %}}
   説明の例：

   **として** _営業担当者のAlex_

   **私は** _販売提案のPDFバージョンをダウンロードしたい_

   **そうすることで** _見込み客にメールで送信できる_
   {{% /callout %}}

   説明は、チームが誰のために構築しているか、なぜそのユーザーがソフトウェアにこの機能を望んでいるか、そしてそれが何を達成するのに役立つかを理解するのに役立ちます。説明で名前を使用する場合、その名前は「営業担当者のAlex」のようにチームが作成した[ペルソナ](/practices/personas/)を表すべきであり、ランダムな名前ではなく、そのペルソナが対象ユーザーであるすべてのストーリーで一貫している必要があります。

   {{% callout %}}
   ヒント：ストーリーの「そうすることで …」部分を、アプリの外で起こることについてにしてみてください。これにより、ユーザーにとっての価値を理解していることを確認できます。「そうすることで …」部分を書くのに苦労している場合は、ストーリーが本当に価値があるかどうか自問してください。
   {{% /callout %}}

   {{% callout %}}
   ヒント：ユーザーは人間である必要はありません！システムのアクターとコンシューマーは、それ自体が他のシステム、ソフトウェア、またはデバイスである場合があります。これは、イベントベースまたはIoTシステムで一般的です。これらのシステムのストーリーを書く方法については、[イベントベースシステムのユーザーストーリーを書く](/guides/writing-agile-user-stories/)に関するTanzuガイドを参照してください。
   {{% /callout %}}

4. **受け入れ基準を書きます。** これらは、エンジニアが開発中に自動テストを書くために使用し、プロダクトマネージャーがストーリーが提供されたときに受け入れテストに使用するシナリオです。受け入れ基準は、ユーザーの視点から「完了」がどのように見えるかを説明します。これらは、チームが何をする必要があるかを理解し、ブロッカーと依存関係を特定し、複雑さを理解して見積もり、作業がどのようにテストされ受け入れられるかを理解し、テスト駆動開発アプローチについて考えるのに役立ちます。

   {{% callout %}}
   受け入れ基準の例：

   **前提** _提案概要ページを訪問する_

   **とき** _「PDF Download」というラベルのボタンをクリックする_

   **ならば** _販売提案のPDFファイルが私のコンピューターにダウンロードされる_
   {{% /callout %}}

5. **必要に応じてサポートドキュメントとメモを追加します。** 必要に応じて、ユーザーストーリーを明確にするための追加情報を含めます。これには、デザインモックアップが最もよく含まれますが、ストーリーに関する一般的なメモ、統合に関連するドキュメントなども含まれる場合があります。

   場合によっては、ストーリーの一部ではないことについてのメモを追加すると役立ちます。スコープ外のすべてのことのリストを書くことは避けてください。ただし、ストーリーの一部のように見えるが実際にはそうでない1〜2つのことがある場合、それらを呼び出すことで明確性を提供できます。

   完全な例は次のとおりです：
   {{% callout %}}

   **ストーリータイトル:** _営業担当者はPDFとして販売提案をダウンロードできる_

   説明：

   **として** _営業担当者のAlex_

   **私は** _販売提案のPDFバージョンをダウンロードしたい_

   **そうすることで** _見込み客にメールで送信できる_

   受け入れ基準：

   **前提** _提案概要ページを訪問する_

   **とき** _「PDF Download」というラベルのボタンをクリックする_

   **ならば** _販売提案のPDFファイルが私のコンピューターにダウンロードされる_

   リソース：

   - 他の製品のこの機能の例：`<リンク to example>`
   - 開発者メモ：他のチームが使用しているPDF変換ライブラリはこちら：`<リンク to resource>`
     {{% /callout %}}

   {{% callout %}}
   ヒント：明確性と高忠実度の実装のために、ユーザーインターフェイスコンポーネントを持つほとんどのユーザーストーリーには、デザイナーからの何らかのモックアップまたはドキュメントを含める必要があります。これは、ワイヤーフレーム、高忠実度モックアップ、クリック可能なプロトタイプ、またはデザインシステムのコンポーネントへの参照など、何でもかまいません。
   {{% /callout %}}

## 成功/期待される成果

以下の場合、良いユーザーストーリーがあることがわかります：

- 製品チーム全体がストーリーを読んで、それがユーザーに提供する価値を理解できる
- IPMでのストーリーに関する議論がスムーズで、詳細を明確にすることについてであり、全体的なアプローチを疑問視することではない - ここに到達するのに苦労している場合は、ストーリーグルーミングをスムーズにするために[IPM事前計画](/practices/iteration-pre-planning/)を検討してください
- エンジニアは、ストーリーからいつ開発が完了するかを判断できる
- 提供されたストーリーを簡単に受け入れることができる
- チームは週に複数のユーザーストーリーを提供する
- バックログのストーリーのほとんどは、他のストーリーと独立して並行して完了できる
- ストーリーは実装の詳細には入らず、代わりに何を構築するかを説明する（_どのように_構築するかではない）

## ファシリテーターのメモとヒント

**INVEST**は、良いユーザーストーリーの品質を覚えるためのニーモニックです。

**Independent（独立）** – 他のストーリーへの依存関係を持たない。任意のストーリーは、それを提供するために他のストーリーへの依存関係を持つべきではありません。開発者ペアは、バックログの上からストーリーを選択し、それが説明する価値を提供するために必要なすべてを行うことができるはずです。バックログ内の他のストーリーに触れることなく、またはコード内で別の開発者の邪魔をすることなく。自分のバックログ内の依存関係を回避するのに苦労している場合は、ストーリーをより独立したものに再スライスする方法を検討してください。

**Negotiable（交渉可能）** – フィーチャーの特定の契約ではない。ストーリーは、提供する価値の断片の共有理解の軽量ドキュメントであり、エンジニアとPM（または製品チームとステークホルダー）の間の提供されるものについての契約的合意ではありません。ストーリーは、開発が始まるまで、ユーザー、ステークホルダー、またはチームからの入力からの新しい情報に基づいて、必要に応じて頻繁に更新する必要があります。開発が始まったら、それに取り組んでいる人々が変更を認識し理解していない限り、ストーリーの変更を避けてください。その場合でも、スコープクリープと新しい受け入れ基準と実装に基づく再見積もりの必要性に注意してください。

**Valuable（価値がある）** – ユーザーに実際の価値を提供し、技術の水平スライスではない。各ストーリーは、提供されると、実際の価値を提供する必要があります。ストーリーは水平スライス（例：フロントエンド、バックエンド）に分割するべきではありません。フルスタックストーリーは、アプリが常にデプロイ可能な（そして潜在的にリリース可能な）状態にあることを保証し、チームをコード行の提供ではなく、作業の成果に集中させます。

**Estimatable（見積もり可能）** – 良い近似値に見積もることができる。チームの開発者は、関与する労力や複雑さの見積もりを提供できるほど、ストーリーの範囲を十分に理解する必要があります。見積もりを可能にするために過度に詳細にすることに注意してください - 実装の詳細は開発者に任せ、ストーリーに書き込むべきではありません。

**Small（小さい）** – 可能な限り小さく、イテレーション内に収まる。ストーリーは、価値を提供しながら可能な限り小さくする必要があります。理想的には、各イテレーションで複数のストーリーを提供します。これにより、短いフィードバックサイクルが可能になり、チームが迅速に学習し、必要に応じて進路修正できます。小さなストーリーは、テストまたはステージング環境への継続的デリバリーもサポートします。

{{% callout %}}
ヒント：ストーリーが大きくなりすぎた良い兆候は、受け入れ基準のブロックがいくつかある場合（特に多くの「AND」）、開発者によって高い複雑さと見積もられた場合（すなわち、フィボナッチポインティングで8）、またはIteration Planning Meeting中に継続的で発散する会話を生成する場合です。大きすぎるストーリーは、タイトなフィードバックループと明確なテストシナリオを保証するために、より小さな独立したストーリーに分割する必要があります。
{{% /callout %}}

**Testable（テスト可能）** – 原則として、テストがまだ書かれていなくても。これは、すでにテストを書いたという意味ではありませんが、提供されたらストーリーをテストする方法がなければなりません。
